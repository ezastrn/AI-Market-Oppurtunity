1. PRODUCT OVERVIEW
================================================================================

1.1 Description
---------------
AI Market Opportunity Intelligence is a reproducible, data-driven workflow for
PRELIMINARY market opportunity screening. It analyses the geographic
distribution of businesses, public facilities and points of interest from
OpenStreetMap (OSM) to identify areas that show (a) relatively low OBSERVED
competitor coverage and (b) relevant supporting context, and therefore deserve
further investigation.

Outputs: interactive map, quantitative indicators, ranked candidate areas,
explainable scores, and a structured market intelligence report.

The system MUST always distinguish between:
  - OBSERVED DATA      (what the dataset actually contains)
  - ANALYTICAL ESTIMATES (what is computed from the data under stated assumptions)
  - HYPOTHESES         (what still requires real-world validation)

1.2 What "AI" means in this project
-----------------------------------
The analytical core is classical spatial analytics (GIS, distance and density
metrics, weighted scoring). It is NOT a machine learning prediction model.
"AI" refers to the role of the AI coding agent, which assists with research,
implementation, analysis interpretation and report drafting. All reports and
documentation MUST state this clearly so readers are not misled about the
method.

1.3 Problem Statement
---------------------
Business location decisions are often made from intuition or incomplete
competitor information. This leads to entering saturated areas, overlooking
possibly underserved areas, and difficulty turning raw geographic data into
actionable recommendations. This project provides a repeatable workflow for
preliminary, evidence-based screening.

1.4 Vision
----------
Turn public geographic data into understandable, explainable and honestly
qualified market intelligence that tells users where further research is
worthwhile and why.

1.5 Core Value Proposition
--------------------------
The product does not merely plot businesses. It evaluates spatial patterns,
compares candidate areas, explains what drives each ranking, reports how much
the evidence can be trusted, and states its limitations explicitly.

1.6 Fundamental Interpretation Rule
-----------------------------------
A high opportunity score means: "low OBSERVED competition in OSM, plus
supporting context, in an area that passes basic suitability filters." It does
NOT mean demand, revenue, profit or business success. No output may state or
imply otherwise.

2. OBJECTIVES AND SUCCESS CRITERIA
================================================================================

2.1 Objectives
--------------
O1. Collect and process public geospatial data for a defined study area.
O2. Identify and classify businesses of one selected category.
O3. Measure competitor concentration, proximity and distribution.
O4. Identify eligible candidate areas with relatively low observed competition
    and relevant context.
O5. Rank candidates with a transparent, configurable scoring method.
O6. Visualize results on an interactive map with supporting charts.
O7. Generate a structured report with findings, recommendations and limits.
O8. Ensure every finding is traceable to data and documented assumptions.

2.2 Success Criteria
--------------------
The project succeeds when ALL of the following hold:
  - Data collection and processing can be repeated from documented steps.
  - The user can change study area, category and parameters via configuration.
  - The pipeline produces a valid cleaned dataset and an interactive map.
  - Candidate areas have explainable scores, ranks and data-sufficiency labels.
  - At least 3 evidence-based candidate areas are produced when the sufficiency
    gates (Section 8.1) pass; otherwise the system explicitly reports
    "insufficient data" and produces NO ranking.
  - Every major recommendation cites measurable indicators.
  - The report separates facts, interpretations and hypotheses.
  - A new user can reproduce the analysis from the README.

6. DATA REQUIREMENTS
================================================================================

6.1 Primary Source: OpenStreetMap
---------------------------------
Retrieve (as relevant to the category):
  - Businesses in the selected category.
  - Complementary businesses and points of interest (context features).
  - Public facilities relevant to the category.
  - Road network (at least highway classes needed for accessibility).
  - Buildings and/or land-use polygons (needed for the eligibility filter).
  - Administrative boundary (city and, if available, districts).

Access method: Overpass API or OSMnx (or a regional extract such as one from
Geofabrik if API limits block retrieval). Before choosing, the agent MUST:
  - Check that the endpoint is currently reachable (execute a test request).
  - Review current usage policy and rate limits.
  - Choose a method, and document the reason in docs/decision_log.md.
Large queries SHOULD be cached to data/raw/. Do not hammer public endpoints.

6.2 Optional Secondary Sources [COULD]
--------------------------------------
Use only if they add clear analytical value and can be accessed lawfully and
reproducibly (e.g., BPS population statistics, open administrative boundaries).
Secondary data MUST NOT be fabricated or assumed to exist. If not retrieved,
state that in the report.

6.3 Normalized Business Dataset Fields
--------------------------------------
  feature_id          Stable source identifier (e.g., OSM type + id)
  name                Name if available (nullable)
  category            Normalized category
  latitude            WGS84 latitude (of the representative point)
  longitude           WGS84 longitude (of the representative point)
  source              Original data source
  source_tags         Relevant original tags (e.g., JSON string)
  retrieved_at        Retrieval timestamp (ISO 8601, with timezone)
  geometry_type       point / polygon / other
  district            District (kecamatan) assigned by spatial join, if known
  data_quality_flag   One or more flags (see 6.4)

Polygon features (e.g., a shop mapped as a building outline) MUST be converted
to a representative point (inside the polygon) for analysis. The original
geometry_type MUST be preserved in the record.

6.4 Data Quality Rules
----------------------
The pipeline MUST:
  1. Remove invalid or empty geometries and out-of-range coordinates.
  2. Flag/remove records outside the study boundary (documented separately
     from the boundary buffer used for competitor retrieval).
  3. Detect duplicates using these ordered rules:
       a. Identical source identifier -> duplicate.
       b. Same normalized name AND same category AND distance <= 30 m
          (INITIAL, configurable) -> probable duplicate; keep one, log merge.
       c. A polygon and a point of the same category within 30 m with the
          same/missing name -> probable duplicate; prefer the record with more
          complete attributes.
     Unnamed records MUST NOT be deduplicated by name alone.
  4. Normalize tags to categories using the documented mapping.
  5. Keep unnamed records (flag them as "missing_name"); document treatment.
  6. Record missing or ambiguous attributes via data_quality_flag.
  7. Report counts: retrieved, invalid removed, outside boundary, duplicates
     merged, retained.
  8. Preserve source identifiers for traceability.
  9. Never interpret absence of OSM records as absence of real businesses.

6.5 Boundary Verification
-------------------------
The agent MUST verify the Kota Malang boundary: confirm the relation/admin
level, that the geometry is valid and a single coherent area (or documented
multipolygon), and sanity-check its area against publicly reported city area
(approximately 110 km2; accept within about +/-10% or document why not).
Record the source and retrieval date. If the OSM boundary is unsuitable, use a
documented alternative.

6.6 Data Integrity and Storage
------------------------------
  - data/raw/        : untouched source snapshots + retrieval metadata file
                       (query, endpoint, timestamp, software versions).
  - data/processed/  : cleaned datasets.
  - data/outputs/    : indicators, scores, rankings, maps, charts.
  - Raw data MUST NOT be modified after retrieval.
  - Respect OSM license: data is (c) OpenStreetMap contributors, ODbL. The
    README, map and report MUST include this attribution. Check redistribution
    terms before committing any dataset to a public repository; prefer
    committing code + retrieval scripts and a small sample over large raw dumps.

6.7 Known Data Limitations (must be disclosed in the report)
-----------------------------------------------------------
OSM is a community-maintained map, not a complete registry of operating
businesses. Coverage varies by area and category; closed businesses may remain
mapped; open ones may be missing; tagging is inconsistent. Building and
land-use coverage may also be incomplete, which affects the eligibility filter.

7. ANALYTICAL METHODOLOGY
================================================================================

7.1 Geographic Preprocessing
----------------------------
  - Reproject all layers to the projected CRS (config: crs.projected) before
    any distance or area computation. NEVER compute local distances using
    Euclidean distance on raw latitude/longitude.
  - Build a regular square grid over the boundary in the projected CRS with
    cell size grid.cell_size_m. Keep cells with at least
    grid.min_inside_fraction of their area inside the boundary. Clip or flag
    partial cells, and document the handling.
  - Each cell has a stable ID and a centroid. Distances are measured from the
    cell centroid unless stated otherwise.
  - Keep the distinction clear: existing business locations are POINTS; grid
    cells are AREAS used to summarize surroundings. A cell is NOT a verified
    business address.

7.2 Competition Indicators
--------------------------
Competitors are mapped businesses of the selected category. To limit edge
effects, competitors are counted from the study area PLUS boundary_buffer_m
around it, while candidate cells remain only inside the boundary.

For each cell compute:
  C1. competitor_count      : competitors within competitor.radius_m of the
                              cell centroid.
  C2. competitor_density    : C1 divided by the search circle area (per km2).
  C3. nearest_competitor_m  : distance to nearest mapped competitor.
  C4. mean_nearest_k_m      : mean distance to nearest k competitors
                              (k = 3, INITIAL), only if at least k exist.

Primary competition inputs for scoring: C1 and C3. C2 and C4 are reported as
supporting statistics. These describe MAPPED competitor distribution, not true
market saturation.

7.3 Eligibility Filter (prevents "empty land" false opportunities)
------------------------------------------------------------------
Low competition can simply mean nobody lives or works there (farmland, forest,
cemetery, industrial or military zones, water). Therefore a cell MUST pass an
eligibility filter BEFORE it can be ranked. Cells failing it remain on the map
(greyed) but are NOT ranked.

A cell is ELIGIBLE if all of these hold (INITIAL VALUES, configurable):
  E1. Inside-boundary fraction >= grid.min_inside_fraction.
  E2. Built-environment evidence, satisfied by AT LEAST ONE of:
        a. OSM building count in the cell >= 20, OR
        b. Share of cell area in residential/commercial/retail land use >= 20%,
           OR
        c. Total mapped road length in the cell >= a threshold chosen from the
           road-length distribution (e.g., the 25th percentile of cells that
           contain buildings).
  E3. Share of cell area in excluded land use (farmland, forest, cemetery,
      industrial, military, reservoir/water) < 50%.

The agent MUST inspect the distributions first and may adjust thresholds, with
justification logged. If building/land-use coverage is too sparse in OSM to
support E2a/E2b, fall back to E2c and disclose this as a limitation. The number
of eligible versus ineligible cells MUST be reported.

7.4 Contextual Suitability Indicators
-------------------------------------
Context features are category-specific and MUST each have a documented
rationale in docs/methodology.md and config. Do not assume a feature is
positive for every category. Example mappings (for the agent to verify against
actual data, not fixed truths):

  Coffee shop / cafe:
    + universities, colleges, schools (amenity=university/college/school)
    + offices, coworking (office=*, amenity=coworking_space)
    + retail/commercial POIs (shop=*)
  Laundry:
    + dormitories, apartments, boarding houses (building=dormitory/apartments)
    + universities/colleges
    + residential building density
  Convenience store:
    + residential building density
    + schools, clinics, bus stops
  Pharmacy:
    + clinics, hospitals (amenity=clinic/hospital/doctors)
    + residential building density

Computation:
  - For each feature type f, count_f = number of features within
    context.radius_m of the cell centroid.
  - Normalize each count_f (Section 7.5) and combine into
    Contextual Suitability using documented feature weights (INITIAL: equal
    weights among the chosen features).
  - If a feature type has zero records in the entire dataset, EXCLUDE that
    feature from the combination and log it; do not treat it as zero-quality
    or as favorable.
  - A cell with zero context features gets a low (not missing) contextual
    value, provided the feature types exist in the dataset.

7.5 Normalization
-----------------
All indicators MUST be transformed to a [0, 1] scale where HIGHER ALWAYS MEANS
MORE FAVORABLE. Default method: winsorized min-max over ELIGIBLE cells only:
  1. Clip values to the 5th and 95th percentile (config).
  2. Min-max scale to [0, 1].
  3. For "lower is better" indicators (e.g., competitor_count), invert:
     value = 1 - scaled.
Alternative (config option): percentile rank. If an indicator has zero variance
among eligible cells, EXCLUDE it, log it, and renormalize weights (7.7).
The direction and transformation of every indicator MUST be documented in a
table in docs/methodology.md.

7.6 Opportunity Score
---------------------
Components (each in [0, 1]):
  Competition Gap (CG)
      CG = 0.5 * norm_up(nearest_competitor_m)
         + 0.5 * norm_down(competitor_count)
      (INITIAL; the 50/50 split is configurable).
  Contextual Suitability (CS)
      Combined normalized context counts from 7.4.
  Accessibility (AC)
      AC = norm_down(distance from cell centroid to the nearest road with
           highway in {primary, secondary, tertiary}).
      Optional supporting statistic: road length density within 500 m.
      This is a physical connectivity proxy only, not travel time.

Score (weighted average, weights sum to 1):
  Opportunity Score = w1*CG + w2*CS + w3*AC   (scaled 0-100 for display)

Baseline weights: approximately equal (0.34 / 0.33 / 0.33). The agent MUST NOT
present these as optimal; they are a neutral baseline tested via scenarios
(Section 8.3).

Traceability: for every cell store CG, CS, AC, the raw indicator values, the
weights used, and each component's weighted contribution to the score.

7.7 Missing Indicator Handling
------------------------------
  - NEVER silently assign a favorable value to a missing indicator.
  - If exactly one of CG, CS, AC cannot be computed for the whole run (e.g., no
    context data exists): exclude it, renormalize the remaining weights to sum
    to 1, flag the run "reduced_model" and state this in all outputs.
  - If CG cannot be computed, OR two or more components are unavailable, mark
    the run INSUFFICIENT and produce no ranking.
  - Cell-level missing values: the cell is excluded from ranking and listed
    with a reason.

7.7a Ranking
------------
Rank ELIGIBLE cells by score (descending). Ties are broken by (1) higher CG,
then (2) higher data sufficiency level, then (3) lower cell ID (deterministic).
For each candidate cell report the fields listed in Section 14.4.

Overlapping/adjacent top cells: to avoid presenting one hotspot as 10
candidates, group contiguous top-ranked cells into candidate zones (documented
rule, e.g., merge cells that share an edge and are all within the top-N), and
rank zones by the mean or max score. If this is judged too complex for MVP,
mark it [SHOULD] and instead present top cells with a note about clustering.

8. CONFIDENCE, SUFFICIENCY AND ROBUSTNESS
================================================================================

Opportunity (score) and evidence confidence are SEPARATE concepts. A cell may
have a high score and weak evidence.

8.1 Run-Level Data Sufficiency Gates (ranking is allowed only if all pass)
--------------------------------------------------------------------------
INITIAL VALUES, configurable:
  G1. Cleaned competitor records >= sufficiency.min_competitors (30).
  G2. Eligible cells >= sufficiency.min_eligible_cells (50).
  G3. At least 2 of the 3 score components computable (see 7.7).
  G4. Competitors present in at least 4 of 5 districts.
If any gate fails: output "INSUFFICIENT DATA", list failed gates, and do not
rank. Provide a recommended alternative (e.g., different category, larger
cell size) instead of fabricating candidates.

8.2 Cell-Level Data Sufficiency Label (not a percentage)
--------------------------------------------------------
Assign each ranked candidate a label HIGH / MEDIUM / LOW using documented,
rule-based factors (count how many hold):
  F1. Cell is at least one competitor-radius away from the study boundary
      (low edge-effect risk).
  F2. Context features have non-trivial coverage (at least 2 distinct context
      feature types with at least 1 record inside the context radius).
  F3. Local data completeness: at least 50% of nearby mapped businesses have
      name and valid category tags (INITIAL).
  F4. Rank stability: cell is in the top-N in at least 70% of robustness
      scenarios (see 8.3).
  Label: HIGH if 4 hold, MEDIUM if 2-3 hold, LOW if 0-1 hold.
Do NOT output an arbitrary "confidence %". Explain each label in plain words.

8.3 Robustness / Sensitivity Checks
-----------------------------------
Run scenarios and compare rankings:
  S1. Competitor radius in {300, 500, 1000} m.
  S2. Grid size in {250, 500, 1000} m (compare at zone/district level, since
      cells differ).
  S3. Weight scenarios:
        baseline          (0.34, 0.33, 0.33)
        competition-heavy (0.50, 0.30, 0.20)
        context-heavy     (0.30, 0.50, 0.20)
        no-accessibility  (0.50, 0.50, 0.00)
  S4. Leave-one-out: remove each context feature in turn.
Metrics (compute and report):
  - Top-N overlap (Jaccard) between each scenario and the baseline.
  - Spearman rank correlation of scores between scenarios.
  - Per-cell "top-N frequency" across scenarios (feeds F4).
Interpretation (INITIAL thresholds): median Jaccard >= 0.5 -> "reasonably
stable"; 0.3 to 0.5 -> "moderately sensitive"; < 0.3 -> "highly sensitive". If
highly sensitive, the report MUST say conclusions depend strongly on
assumptions and downgrade recommendation strength accordingly.
[SHOULD] for S2 and S4; [MUST] for S1 and S3.

9. AI AGENT OPERATING RULES
================================================================================

9.1 Responsibilities
--------------------
Research and planning, implementation, analysis and interpretation, reporting
(see Sections 18 and 14).

9.2 Hard Constraints (the agent MUST NOT)
-----------------------------------------
  - Invent records, statistics, locations or results.
  - Claim code ran successfully without execution evidence.
  - Claim an API is available without testing it.
  - Treat generated text as a substitute for actual analysis.
  - Hide errors or silently replace failed retrieval with fabricated or
    synthetic data.
  - Present the score as a guarantee of success.
  - Claim high demand solely because many facilities are nearby.
  - Claim that lack of mapped competitors proves absence of competition.
  - Mix synthetic test data into real results (synthetic data is allowed only
    in unit tests and must be clearly labelled and kept in tests/).
  - Commit secrets, credentials or non-redistributable data.

9.3 Verification Discipline
---------------------------
  - After each pipeline stage, run it and capture evidence (row counts, file
    paths, printed summaries). Include key evidence in docs and the final
    summary.
  - Run tests with pytest and report the actual pass/fail output.
  - An acceptance criterion is "met" ONLY when verified by execution,
    inspection or test (see Section 15).
  - Every number in the report MUST be generated from pipeline output files
    (e.g., by a report script reading data/outputs/), never typed from memory.

9.4 Logging and Decisions
-------------------------
Maintain docs/decision_log.md. Log: chosen access method, final category and
why, every change to an INITIAL VALUE, threshold overrides, deviations from
this PRD, and unresolved issues. Each entry: date, decision, reason, impact.

9.5 Stop-and-Report Conditions
------------------------------
Stop and report to the Project Owner (do not improvise) when:
  - The data access method fails after reasonable retries and documented
    alternatives are exhausted.
  - No candidate category passes the selection rule.
  - Sufficiency gates fail.
  - The boundary cannot be verified.
  - A requirement here would force violating a data license or usage policy.
When external data cannot be retrieved: report the failure, explain the impact,
and propose a documented alternative.

9.6 Communication Style
-----------------------
Final summaries MUST be honest and concise: what was done, evidence, what
failed or is uncertain, and what remains. Do not overstate.

16. TESTING STRATEGY
================================================================================

16.1 Unit tests (pytest)
------------------------
  - Config: invalid weights (do not sum to 1), non-positive radius, missing
    category mapping -> raises clear error.
  - Cleaning: invalid coordinates removed; polygon -> representative point;
    exact-ID duplicate removed; near-duplicate (same name, <= 30 m) merged;
    unnamed records retained and flagged; category normalization.
  - Normalization: output within [0,1]; direction correct (more competitors
    -> lower value); zero-variance indicator excluded.
  - Scoring: weights sum respected; reweighting when a component is missing;
    missing component never raises the score.
  - Ranking: deterministic tie-breaking; only eligible cells ranked.
  - Export: CSV round-trip retains columns and row count.

16.2 Spatial tests
------------------
  - A pair of points with a known real-world distance is measured within a
    stated tolerance after projection.
  - Features outside the boundary are flagged.
  - Distances are non-negative.
  - Every point is assigned to exactly one cell (or none if outside).
  - Grid cells have valid geometries; empty cells are handled.
  - Buffer-based edge handling: a competitor just outside the boundary
    affects an edge cell's competitor_count as intended.

16.3 Integration test
---------------------
Run the full pipeline on a small, labelled, known (synthetic or tiny real)
dataset with predictable expected output before running on the full city.
Synthetic data stays inside tests/ and MUST NOT leak into real outputs.

16.4 Analytical validation
--------------------------
  - Adding a competitor next to a cell lowers that cell's CG (and score).
  - Removing a context feature type changes CS as expected.
  - A missing indicator does not increase a cell's rank.
  - Top candidates are not trivially artifacts of grid alignment (compare with
    a shifted grid origin; report the result).
  - Sanity check: no top candidate lies in a clearly non-built area (inspect
    the top 10 visually on the map).
  - [SHOULD] Manual spot-check: compare the top candidates and 3 low-ranked
    cells against a second source (e.g., satellite imagery or other map
    services) viewed manually, and record observations as a qualitative
    check (not as proof).

19. GLOSSARY
================================================================================
Candidate area      A grid cell (or group of cells) that ranks highly under the
                    documented scoring method; NOT a verified business address.
Competition Gap     Normalized measure of low observed competitor coverage.
Contextual          Normalized measure of presence of category-relevant
Suitability         supporting features nearby.
Accessibility       Normalized measure of proximity to major roads (physical
                    connectivity proxy).
Eligibility filter  Rule set that excludes cells without evidence of built
                    environment so empty land is not ranked.
Data sufficiency    Rule-based label (HIGH/MEDIUM/LOW) describing evidence
                    strength; separate from the opportunity score.
Edge effect         Distortion near the study boundary caused by ignoring
                    features just outside it.
OSM                 OpenStreetMap, a community-maintained open map database.
ODbL                Open Database License governing OSM data.
Projected CRS       Coordinate system in meters (e.g., UTM) suitable for
                    distance/area calculations.
Winsorizing         Clipping extreme values to chosen percentiles before
                    scaling.
Jaccard overlap     Size of intersection divided by size of union of two sets;
                    used to compare top-N lists.
